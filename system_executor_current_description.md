# System Executor — Full Module Description (Research + Technical Perspective)

## Role in the Broader System

The System Executor is the last link in a five-module pipeline for automated industrial disassembly (de-remanufacturing). It receives a Masterplan — a sequence of machine-level instructions generated by the upstream System (De)production Planner — and executes it on physical hardware via OPC UA protocol. It is the Cyber-Physical bridge: everything upstream is digital planning, everything downstream is physical actuation.

The Executor does not decide *what* to do — it decides *how* to do it reliably, safely, and observably.

## Architecture

Distributed multi-agent system with three tiers communicating via WebSocket and OPC UA:

```
SystemAgent (supervisor)
    ↓ WebSocket (ws://localhost:8000/ws)
API Server (FastAPI, port 8000) — pure message broker
    ↓ WebSocket
Resource Agents (one per physical machine)
    ↓ OPC UA (opc.tcp://192.168.0.200:4842)
PLC / physical hardware
```

### SystemAgent (Supervisor)
Parses the Masterplan, dispatches commands to the appropriate Resource Agent one step at a time, waits for completion feedback (SUBPLAN_COMPLETED or ERROR), and proceeds or halts accordingly. It registers as "SUPERVISOR" on the broker. Currently being evolved from an interactive CLI process to a headless service controlled via a Web UI.

### API Server (Broker)
FastAPI application with a single WebSocket endpoint (`/ws`). Its role is strictly limited to message routing — it receives, identifies, and forwards messages between the SystemAgent, Resource Agents, and (in the near future) UI clients. It maintains no business logic. A volatile SQLite database stores the registry of connected resources and their declared capabilities, reset at every server startup.

A second WebSocket endpoint (`/ws/ui`) is being added for UI clients, keeping the control channel (`/ws`) isolated from observation traffic.

### Resource Agents
Each physical machine is represented by a Resource Agent — a Python process that connects to the API Server, declares its capabilities, and translates high-level service calls into low-level OPC UA read/write operations on the PLC.

Key design pattern: **service auto-discovery via introspection**. Any method named `service_<NAME>` on the agent class is automatically detected, its parameters inspected, and the resulting schema sent to the server at registration. This means adding a new service requires only writing a Python method — no registration code, no schema files, no database updates.

Each agent also declares the physical limits (ranges) of its components — axis travel limits, maximum velocities, acceleration bounds. These are defined once in the agent's constructor (Single Source of Truth) and propagated to the database for external consumption by planners and validators.

The base class (`OPCUAMachineClient`) provides:
- Write-and-verify pattern: every OPC UA write is followed by a subscription-based check that the value actually changed on the PLC (with polling fallback)
- Sequential execution engine: processes a list of steps, calling the appropriate `service_*` method for each, with error handling that halts on first failure
- Configurable timeout (currently 360s, being evolved into three semantic levels)

## Physical Hardware

All hardware is controlled through a Siemens PLC (OPC UA server). Node IDs are mapped in a central configuration file (~60 nodes across 3 machines):

- **DOOSAN collaborative robot (cobot):** ~30 nodes (state, joint positions, Profinet/Wago I/O). Resource Agent not yet implemented.
- **SEIT induction heater:** 4 nodes (target temperature, enable, current temperature reading). Resource Agent not yet implemented.
- **MULLUTENSIL disassembly machine:** ~30 nodes (6 axes — X, Y, Z, 360° rotation, press, pneumatic screwdriver — with position/velocity/acceleration/deceleration/step signals, pneumatic air, sensors). Fully implemented Resource Agent (v2) with 5 exposed services: SET_PARAMS, MOVE, ACTIVATE, DEACTIVATE, WAIT.

The disassembly machine agent models two component types:
- **AxisElectrical** (X, Y, Z, 360, PRS): motorized axes with configurable velocity, acceleration, deceleration, and target position. Each has declared min/max ranges for all parameters.
- **AxisAir** (screwdriver): pneumatic binary actuator with activate/deactivate operations.

## Plan Format

The Masterplan is a plain text file — the contractual interface with the upstream System Planner. Format:

```
ResourceName | SERVICE | param1=val1 param2=val2    # direct command
ResourceName | RUN_FILE | subplan.txt                # delegate to external file
# comments are ignored
```

Subplans (referenced via RUN_FILE) follow the same format but without the resource prefix — the target resource is inherited from the masterplan line.

This format is deliberately simple and human-readable. It is a stable contract: changes require alignment with the System Planner module.

## Data Flow (Single Command Lifecycle)

1. SystemAgent reads a line from the Masterplan, parses it (validating against the DB schema of the target resource)
2. SystemAgent sends a `dispatch_command` message via WebSocket to the API Server
3. API Server looks up the target Resource Agent in `connected_clients` and forwards the command
4. Resource Agent receives the command, calls the corresponding `service_*` method
5. The service method writes values to OPC UA nodes on the PLC, then verifies via subscription that the values were applied
6. On completion, Resource Agent sends `feedback` (status: SUBPLAN_COMPLETED or ERROR) back through the API Server to the SystemAgent
7. SystemAgent logs the result and proceeds to the next step (or halts on error)

## Current Capabilities

- End-to-end execution of multi-step masterplans on physical hardware
- Dynamic resource registration and service discovery
- Physical limit declaration and propagation to the database
- Write-and-verify pattern for OPC UA reliability
- Error detection and plan termination on failure
- Support for both direct commands and subplan delegation
- Heartbeat-based health monitoring of connected agents
- Runtime range validation as hardware safety net (agent-side)
- Timeout on supervisor feedback wait (prevents indefinite blocking)

## Known Limitations (Being Addressed)

| Limitation | Impact | Planned Resolution |
|---|---|---|
| Sequential execution only | Cannot command two machines in parallel | Masterplan `PARALLEL {}` blocks (Phase 4) |
| No retry on failure | Single error aborts the entire plan | Configurable per-service retry with backoff (Phase 2) |
| No rollback | No concept of transaction or undo | Under consideration for irreversible operations |
| No reconnection | WebSocket or OPC UA disconnection is fatal | Auto-reconnect with exponential backoff (Phase 2) |
| No UI | Controlled via CLI terminal | Web UI served by FastAPI (Phase 1, in progress) |
| No data logging | OPC UA values visible only in terminal | Observer agent + time-series DB + live dashboard (Phase 1) |
| Only 1 of 3 machines has an agent | DOOSAN and SEIT nodes mapped but no agent code | Phase 4 (requires machine-specific knowledge) |
| Node resolution fail-fast | If any mapped OPC UA node doesn't exist on PLC, server won't start | Make resolution non-fatal before adding new machine agents |

## Key Design Decisions and Rationale

**Why multi-agent rather than monolithic?** Each machine may have different communication patterns, timing requirements, and failure modes. An agent-per-machine architecture isolates failures (one machine's error doesn't crash the entire system), enables independent development and testing, and mirrors the physical modularity of the lab.

**Why the API Server is a pure broker?** Keeping business logic out of the broker makes it a stable, unchanging component. New functionality is added by creating new agents or extending existing ones — the broker just routes messages. This is critical for extensibility when new developers join.

**Why write-and-verify instead of fire-and-forget?** Industrial hardware can fail silently — a PLC might acknowledge a write but not actually actuate. The subscription-based verification pattern detects this. The polling fallback handles cases where subscriptions are unreliable.

**Why Single Source of Truth for physical limits?** Physical limits are safety-critical. If they're duplicated (in the agent, in the DB, in the planner), they will eventually diverge, and the wrong limit will be trusted. By declaring limits only in the agent's constructor and deriving everything else from that, there's one place to update and one place where errors can originate.

**Why a two-level range validation?** Defense in depth. The DB-side check (Phase 1.3) gives fast feedback and good UX — invalid plans are rejected before execution starts. The agent-side check (Phase 0.3) is the last line of defense before the hardware — it protects the machine even if the DB is stale, corrupted, or bypassed.

## Integration Points (Upstream and Downstream)

- **Input (upstream):** Masterplan `.txt` from the System (De)production Planner. This is a stable contractual interface — format changes require cross-module alignment.
- **Capability advertisement (upstream):** The database of registered resources, services, parameters, and ranges is available for the System Planner to query when generating plans. This creates a feedback loop: the planner knows what the executor can do.
- **Output (downstream, future):** Digital Twin integration. The DT will connect as a simulation layer, receiving the same Masterplan format and producing feedback in the same format as real hardware. This enables Virtual Commissioning: validate plans in simulation before physical execution.
- **Observation (lateral, in progress):** Observer agent for data logging, Web UI for real-time monitoring. These are read-only consumers that do not interfere with the control channel.

## Technology Stack

- **Language:** Python 3, fully async (asyncio/await)
- **Communication:** FastAPI (WebSocket), asyncua (OPC UA client)
- **Database:** SQLite (volatile runtime state, reset on startup; separate persistent DB for data logging)
- **Hardware interface:** Siemens PLC via OPC UA
- **Frontend (planned):** React (Vite), served as static files by FastAPI
- **OS:** Windows (lab environment)
- **Development:** VSCode, no test suite currently (planned in Phase 3)
